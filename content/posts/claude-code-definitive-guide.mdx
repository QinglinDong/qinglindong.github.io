How do you make an AI agent work reliably, autonomously, and for hours on complex tasks?

This is the root problem of **long-horizon autonomous agents** — and it is the problem Claude Code exists to solve. Since launching in February 2025, Claude Code has evolved from a terminal chatbot into a full autonomous development platform. Every feature it ships addresses a specific failure mode of AI agents working on real-world tasks.

This post covers every major feature, organized by the problem it solves. Bookmark it. You will come back.

---

## The Four Bottlenecks

An AI agent working on a complex, multi-step task hits four independent bottlenecks. Solving one does not solve the others.

| Bottleneck | What Happens | Analogy |
|---|---|---|
| **Memory** | Context window is finite. New information pushes out old information. The agent forgets what it learned 20 minutes ago. | A person with only working memory and no notebook. |
| **Planning** | The more steps a task has, the more the goal drifts. Decisions made at step 50 contradict decisions made at step 5. | Writing 100 lines of code and forgetting why you started. |
| **Execution** | Errors compound. One small mistake causes every subsequent step to diverge. No self-correction mechanism means the agent digs deeper into the wrong path. | Taking a wrong turn in a maze — every step after makes it worse. |
| **Verification** | The agent cannot accurately judge whether it is on the right track. It proceeds confidently toward the wrong answer. | No map, no compass. |

These bottlenecks are **MECE** (mutually exclusive, collectively exhaustive). Every failure mode of an autonomous coding agent traces back to one of these four.

---

## Three Layers of Solutions

Solutions exist at three distinct layers. Claude Code operates primarily at **Layer 2** and **Layer 3**.

| Layer | Strategy | What It Does | Bottlenecks Addressed |
|---|---|---|---|
| **Layer 1: Model** | Make the brain better | Larger context windows, better reasoning via RL, inference-time scaling (o1/o3-style "think longer") | Memory, Planning |
| **Layer 2: Scaffolding** | Add external organs | Persistent memory files, structured workflows, deterministic verification hooks — all outside the model | Memory, Planning, Execution, Verification |
| **Layer 3: Multi-Agent** | Divide and conquer | Multiple specialized agents coordinating — planner, executor, reviewer — each with isolated context | All four (but introduces coordination complexity) |

Layer 1 is Anthropic's job (and Google's, and OpenAI's). Layers 2 and 3 are where Claude Code's features live.

## Layer 1: The Model — What Claude Code Cannot Change

Claude Code does not control the model. But it benefits from every model improvement:

- **Larger context windows** (Gemini's 1M→2M token trajectory) ease the memory bottleneck by giving the agent more "RAM."
- **Better reasoning via RL** (reinforcement learning for long-horizon focus) reduces planning drift.
- **Inference-time scaling** (the o1/o3 paradigm of "thinking longer before answering") improves decision quality on complex steps.

These improvements help, but they are not sufficient. A model with a 2M-token window still forgets if the task takes 4M tokens of reasoning. Better reasoning still drifts over hundreds of steps. That is why scaffolding and multi-agent architecture exist.

## Layer 2: Scaffolding — Where Claude Code Lives

Scaffolding adds structure *around* the model without changing it. Claude Code's scaffolding breaks into three subsystems, each targeting specific bottlenecks.

### 2A. External Memory — Solving the Memory Bottleneck

The memory bottleneck: context window is finite, and new information pushes out old information.

The solution: write important things to "disk" — persistent files that survive context compaction and session boundaries.

#### CLAUDE.md — Teaching Claude Your Project's DNA

CLAUDE.md is a markdown file that Claude reads automatically at the start of every session. It contains persistent context about your project: coding conventions, architecture decisions, build commands, testing instructions, and anything else you would otherwise repeat in every prompt.

Without CLAUDE.md, every new session starts from zero. With it, Claude has institutional memory before you say a word.

**The memory hierarchy:**

| Level | Location | Scope |
|---|---|---|
| User memory | `~/.claude/CLAUDE.md` | All your projects. Global preferences. |
| Project memory | `CLAUDE.md` at repo root | This repo. Tech stack, patterns, build commands. Version-controlled. |
| Rules directory | `.claude/rules/*.md` | Organized, focused rule files for larger projects. |
| Nested directories | `packages/frontend/.claude/rules/` | Monorepo support. Package-specific rules. |

Run `/init` to generate a starter CLAUDE.md, then customize it:

```markdown
# Project: MyApp

## Tech Stack
- TypeScript, React 18, Next.js 14 App Router
- Tailwind CSS for styling
- Prisma ORM with PostgreSQL
- Vitest for testing

## Conventions
- Use named exports, not default exports
- All API routes return `{ data, error }` shape
- Commit messages follow Conventional Commits
- Never use `any` type — use `unknown` and narrow

## Common Commands
- `pnpm dev` — start dev server
- `pnpm test` — run test suite
- `pnpm lint` — run ESLint + Prettier check
- `pnpm db:migrate` — run Prisma migrations
```

Press `#` during a session to add a memory. Type your instruction and hit Enter — Claude writes it to the appropriate CLAUDE.md.

#### Auto-Memory — Claude Writes Notes to Itself

Auto-memory is a persistent directory where Claude records learnings, patterns, and insights *as it works*. Unlike CLAUDE.md (which you write for Claude), auto-memory contains notes Claude writes for itself.

Each project gets its own memory directory at `~/.claude/projects/<project-hash>/memory/`. The first 200 lines of `MEMORY.md` are loaded into Claude's system prompt every session. Claude writes to memory when it discovers something worth remembering: a non-obvious build command, an architectural pattern, a preference you expressed.

This is the "notebook" that the four-bottleneck analogy says is missing. The agent has working memory (context window) *and* persistent storage (auto-memory files).

#### Context Management — Keeping the Window Clean

Context degradation is the primary failure mode of long sessions. As the window fills, response quality drops, costs increase, and Claude starts forgetting earlier instructions.

**`/compact`** — Compresses conversation history, preserving key decisions and discarding noise. Run this every time you finish a task:

```
/compact Focus only on the authentication refactor. Discard everything about styling.
```

Auto-compact triggers at ~95% capacity, but do not wait for it.

**`/clear`** — Hard reset. Use when switching to a completely unrelated task.

**`/context`** — Colored grid showing what is consuming your window. Diagnose why Claude seems confused.

**Re-inject context after compaction** with a `SessionStart` hook:

```json
{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "compact",
        "hooks": [
          {
            "type": "command",
            "command": "echo 'Reminder: use Bun, not npm. Run bun test before committing.'"
          }
        ]
      }
    ]
  }
}
```

#### Tool Use Patterns — Reducing Context Waste

Using `cat` via Bash to read a file wastes context on shell overhead. Claude Code's dedicated tools (Glob, Grep, Read, Edit, Write) return clean, minimal output.

| Task | Use This | Not This |
|---|---|---|
| Search for files by name | **Glob** (`**/*.ts`) | `find` via Bash |
| Search file contents | **Grep** (regex patterns) | `grep` or `rg` via Bash |
| Read a file | **Read** (with line ranges) | `cat` / `head` / `tail` via Bash |
| Edit part of a file | **Edit** (string replacement) | `sed` / `awk` via Bash |
| Write a new file | **Write** (full content) | `echo >` via Bash |
| Run commands | **Bash** | N/A |

Why this matters beyond context savings:
1. **Permissions**: Read and Edit go through the permission system. `cat` via Bash does not.
2. **Parallel execution**: Multiple Glob and Grep calls batch in a single turn.
3. **Hooks**: PreToolUse and PostToolUse hooks trigger on Edit or Write. They cannot trigger on `sed` through Bash.

### 2B. Process Discipline — Solving the Planning and Execution Bottlenecks

The planning bottleneck: the more steps, the more the goal drifts.
The execution bottleneck: errors compound without self-correction.

The solution: enforce structured workflows — think before acting, iterate with verification, maintain explicit plans.

#### Plan Mode — Think Before You Act

Plan Mode restricts Claude to read-only operations. It explores your codebase using Glob, Grep, and Read, creates a detailed implementation plan, and waits for your approval before executing.

For complex changes — refactoring auth, migrating a database schema, restructuring a module — you do not want Claude to start changing files immediately. Plan Mode prevents premature action and gives you a review checkpoint.

Three ways to activate:
1. **Press `Shift+Tab` twice** — cycles through Normal → Auto-Accept → Plan Mode
2. **Type `/plan`** — enters Plan Mode directly
3. **Set in config** — `defaultMode: "plan"` in settings.json

This directly addresses planning drift: the human reviews the plan *before* execution begins, catching goal misalignment early when it is cheap to correct.

#### RALPH Loops — Autonomous Closed-Loop Iteration

RALPH (named after Ralph Wiggum from *The Simpsons*) is an autonomous loop technique. A **Stop hook** intercepts Claude's exit attempts, re-feeds the original prompt, and continues the cycle until the agent outputs a **completion promise** (e.g., `"RALPH_COMPLETE"`).

Without RALPH, you are the loop. For large-scale work — refactoring an entire module, generating test coverage for 40 files, triaging a backlog — this human-in-the-loop overhead is the bottleneck. RALPH removes you.

**Installing the ralph-wiggum plugin:**

```bash
# Install the official plugin
claude plugin add ralph-wiggum

# Or install directly from GitHub
claude plugin add ghuntley/ralph-wiggum
```

The plugin registers a Stop hook and a custom `/ralph-loop` skill. Once installed, invoke it:

```bash
/ralph-loop "Refactor all API handlers to use the new error format. Run tests after each file."
```

**How it works under the hood:**

1. The Stop hook fires every time Claude tries to exit.
2. It checks Claude's final output for the **completion promise** — a specific string (default: `"RALPH_COMPLETE"`) that Claude outputs only when it believes the task is truly finished.
3. If the promise is absent, the hook re-feeds the original prompt with context: "Continue working. You have not finished yet."
4. If the promise is present, the hook allows the exit and the loop terminates.

**Control parameters:**
- `--max-iterations` — safety cap to prevent runaway loops (default varies by configuration)
- `--completion-promise` — the exact string that signals done (default: `"RALPH_COMPLETE"`)

**Manual RALPH setup (without the plugin):**

If you prefer to wire it yourself, the core mechanism is a Stop hook in your `settings.json`:

```json
{
  "hooks": {
    "Stop": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "if ! grep -q 'RALPH_COMPLETE' /tmp/claude_last_output; then echo 'Continue working on the task. Output RALPH_COMPLETE only when fully done.'; exit 0; else exit 0; fi"
          }
        ]
      }
    ]
  }
}
```

The plugin abstracts this away and adds iteration counting, logging, and graceful termination.

Real-world results are striking. Geoffrey Huntley reportedly ran a 3-month RALPH loop that built a complete programming language. YC hackathon teams have shipped 6+ repos overnight for under $300 in API costs. The technique works best for batch operations: large refactors, test coverage generation, documentation sweeps, and support ticket triage.

The core insight: **verification drives everything.** Give Claude a way to verify its own work (tests, linters, type checks), and it can run reliably for hours. This is why RALPH addresses both the planning bottleneck (structured iteration prevents drift) and the execution bottleneck (verification catches errors before they compound).

RALPH is a **closed loop** — no human steering once it starts.

#### Plan-File Loops — Steerable Open-Loop Iteration

Plan-File Loops are the open-loop counterpart to RALPH. The agent writes its plan to a file (e.g., `TODO.md`), works through items one by one, and checks the file for changes between iterations. The human steers by editing the file.

```markdown
# Plan — Auth Refactor

- [x] Extract session logic from middleware
- [ ] Add JWT validation to /api/protected
- [ ] Write integration tests for auth flow
- [ ] Update API docs

<!-- NOTE: skip rate limiting for now, defer to v2 -->
```

Use a Stop hook that re-feeds "read plan.md and work on the next unchecked item." Between iterations, edit the file from your phone. The agent adjusts.

The explicit plan file is an external planning artifact — it prevents goal drift by giving both human and agent a shared, persistent source of truth about what should happen next.

| | RALPH (closed) | Plan-File (open) |
|---|---|---|
| **Control** | None after launch | Edit the file anytime |
| **Best for** | Uniform batch work (same operation × many files) | Multi-step projects with changing priorities |
| **Risk** | Runaway loops, wasted work on wrong path | Agent may re-read file too often, slight overhead |
| **Human role** | Set and forget | Light supervision via file edits |

#### Multi-Turn Agentic Workflows — The Self-Correcting Loop

Claude Code does not just answer questions. It works through tasks in a loop: **gather context → take action → verify results**, chaining dozens of tool calls and course-correcting based on each result.

```
You: "Add rate limiting to the API"

Claude: [Read src/routes/api.ts]
        [Grep "middleware" across codebase]
        [Read src/middleware/auth.ts for pattern reference]
        [Edit src/middleware/rateLimit.ts — create new file]
        [Edit src/routes/api.ts — add middleware]
        [Bash: npm test]
        [Read test output — 2 failures]
        [Edit src/middleware/rateLimit.ts — fix edge case]
        [Bash: npm test]
        [All tests pass]
        "Done. Added rate limiting middleware with sliding window..."
```

Each step informs the next. This addresses the execution bottleneck directly: errors are caught and corrected *within the same workflow*, not compounded silently. The three phases — gather context, take action, verify results — interleave continuously. Claude might gather more context mid-implementation when it discovers something unexpected. This is what makes it agentic rather than generative.

#### Headless Mode — Non-Interactive Execution

The `-p` flag runs Claude Code non-interactively for CI/CD, scripts, GitHub Actions, and cron jobs.

```bash
# Simple question
claude -p "What does the auth module do?"

# Pipe input
cat error.log | claude -p "What caused this crash?"

# Structured JSON output
claude -p "Extract function names from auth.py" \
  --output-format json \
  --json-schema '{"type":"object","properties":{"functions":{"type":"array","items":{"type":"string"}}}}'

# PR review in CI
gh pr diff "$PR_NUMBER" | claude -p \
  --append-system-prompt "You are a security engineer. Review for vulnerabilities." \
  --output-format json

# Continue conversations
claude -p "Now focus on database queries" --continue

# Streaming
claude -p "Explain recursion" --output-format stream-json --verbose
```

**Security note**: In `-p` mode, trust verification is disabled. Use `--allowedTools` to scope permissions explicitly.

### 2C. Verification Mechanisms — Solving the Verification and Execution Bottlenecks

The verification bottleneck: the agent cannot judge whether it is on the right track.

The solution: deterministic guardrails that do not rely on the LLM's probabilistic judgment.

#### Hooks — Deterministic Control Over Non-Deterministic Behavior

Hooks are user-defined shell commands that execute at specific lifecycle points. They fire deterministically — you are not *hoping* Claude remembers to run Prettier; it *always* runs because the hook guarantees it.

LLMs are probabilistic. You can tell Claude "always format with Prettier after editing" in CLAUDE.md, and it will do it ~90% of the time. Hooks make it 100%.

**Hook event lifecycle:**

| Event | When it fires |
|---|---|
| `SessionStart` | Session begins or resumes |
| `UserPromptSubmit` | After you press Enter, before Claude processes |
| `PreToolUse` | Before a tool call executes — **can block it** |
| `PostToolUse` | After a tool call succeeds |
| `Stop` | When Claude finishes responding |
| `Notification` | When Claude needs your attention |
| `SubagentStart` / `SubagentStop` | When sub-agents spawn or finish |
| `ConfigChange` | When a settings file changes |
| `PreCompact` | Before context compaction |
| `SessionEnd` | When the session terminates |

**Auto-format after every edit** (PostToolUse):

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}
```

**Block edits to protected files** (PreToolUse — exit code 2 blocks):

```bash
#!/bin/bash
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')
PROTECTED=(".env" "package-lock.json" ".git/")
for pattern in "${PROTECTED[@]}"; do
  if [[ "$FILE_PATH" == *"$pattern"* ]]; then
    echo "Blocked: $FILE_PATH matches protected pattern '$pattern'" >&2
    exit 2
  fi
done
exit 0
```

**Desktop notification when Claude is waiting** (Notification):

```json
{
  "hooks": {
    "Notification": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "osascript -e 'display notification \"Claude Code needs your attention\" with title \"Claude Code\"'"
          }
        ]
      }
    ]
  }
}
```

There are also **prompt-based hooks** (`"type": "prompt"`) where a small Claude model makes a yes/no decision, and **agent-based hooks** (`"type": "agent"`) where a sub-agent with full tool access verifies conditions before allowing the action.

Hooks are the "compass" from the bottleneck analogy. They provide external, deterministic verification that does not depend on the LLM's judgment.

#### Permission Modes — Safety as Verification

The permission system controls what Claude can do, providing a verification layer that catches dangerous actions before they execute.

| Mode | Behavior |
|---|---|
| `default` | Prompts for permission on first use of each tool. |
| `acceptEdits` | Auto-accepts file edits. Still prompts for bash. |
| `plan` | Read-only. No modifications. No commands. |
| `dontAsk` | Auto-denies anything not explicitly allowed via rules. |
| `bypassPermissions` | Skips all prompts. **Only use in sandboxed environments.** |

Configure allowlists and denylists in `settings.json`:

```json
{
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(git commit *)",
      "Bash(pnpm test *)",
      "Read"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Bash(git push --force *)",
      "Edit(.env)"
    ]
  }
}
```

Rules evaluate: **deny > ask > allow**. First match wins. Toggle with `Shift+Tab` or `/permissions`.

## Layer 3: Multi-Agent Architecture — Divide and Conquer

Multi-agent architecture addresses all four bottlenecks simultaneously by splitting the work across specialized agents with isolated contexts. The trade-off: it introduces **coordination complexity** as a new problem.

### Sub-Agents and the Task Tool

Sub-agents are specialized AI assistants that Claude spawns for specific tasks. Each runs in its own context window with a custom system prompt, specific tool access, and independent permissions.

A single conversation context gets crowded fast. Sub-agents keep each concern isolated: research in one context, implementation in another, the main agent stays clean. This directly solves the **memory bottleneck** (each agent has its own full context window) and the **planning bottleneck** (each agent has a focused, narrow goal).

**Three execution modes:**

1. **Parallel** — 3+ independent tasks with no shared state. Fan out simultaneously.
2. **Sequential** — Tasks with dependencies. Output from agent A feeds into agent B.
3. **Background** — Non-blocking research or analysis. Results surface when ready.

**Built-in agent types:**

| Agent | Purpose |
|---|---|
| `Explore` | Read-only codebase exploration. Uses Glob, Grep, Read. |
| `Plan` | Creates implementation plans without modifying files. |
| `general-purpose` | Full tool access. The default. |

**Custom sub-agents** — create `.claude/agents/security-reviewer/AGENT.md`:

```yaml
---
name: security-reviewer
description: Reviews code changes for security vulnerabilities
model: claude-sonnet-4-20250514
allowed-tools: Read, Grep, Glob
---

You are a security engineer. Review the provided code for:
1. Injection vulnerabilities (SQL, XSS, command)
2. Authentication/authorization issues
3. Sensitive data exposure
4. Insecure dependencies

Report findings with severity, file location, and remediation.
```

Press `Ctrl+B` to background a running agent. Use `/tasks` to see all background processes.

### Worktrees — Isolated Execution Environments

Git worktrees give each agent session its own working directory and branch while sharing repository history.

If two Claude sessions edit the same directory, their file edits collide. Worktrees solve this — each session gets an isolated copy. This directly addresses the **execution bottleneck**: parallel agents cannot corrupt each other's state.

```bash
claude --worktree feature-auth
```

Creates a worktree at `.claude/worktrees/feature-auth` with a new branch. For sub-agents, add `isolation: worktree` to get automatic isolation. For non-git VCS (SVN, Perforce, Mercurial), configure `WorktreeCreate` and `WorktreeRemove` hooks.

### The Agent SDK — Build Custom Multi-Agent Systems

The Agent SDK exposes Claude Code's engine — the agent loop, built-in tools, context management — as a library for TypeScript and Python.

```bash
npm install @anthropic-ai/claude-agent-sdk
```

```typescript
import { query } from "@anthropic-ai/claude-agent-sdk";

const messages = query({
  prompt: "Find and fix security vulnerabilities in auth.py",
  allowedTools: ["Read", "Edit", "Bash"],
  options: { maxTurns: 20 },
});

for await (const message of messages) {
  console.log(message);
}
```

The SDK lets you build multi-agent architectures tailored to your specific needs: a planning agent that decomposes work, execution agents that implement in parallel, and a review agent that validates results. This is the full realization of Layer 3 — purpose-built agent teams for your domain.

## The Capability Layer — Extending Reach and Reducing Friction

Not every feature maps to the four bottlenecks. Some features extend what the agent *can do* (reach) or make the human-agent interaction faster (ergonomics). These are multipliers on top of the three solution layers.

### MCP Servers — Connecting Claude to Everything

MCP (Model Context Protocol) lets Claude Code connect to external tools — databases, browsers, APIs, internal services — via a unified protocol. Think of it as USB for AI tools: one plug, many devices.

Without MCP, Claude can only see filesystem and shell. With MCP, it queries databases, browses the web, searches Confluence, manages cloud infrastructure — all through natural language.

```bash
claude mcp add github -- npx -y @modelcontextprotocol/server-github
```

Or configure in `.mcp.json`:

```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" }
    }
  }
}
```

Three transport modes: **stdio** (default), **SSE**, and **Streamable HTTP**. Tool Search auto-enables when MCP tool descriptions exceed 10% of the context window.

### IDE Integrations — Claude in Your Editor

Native extensions for VS Code and JetBrains eliminate context-switching between editor and terminal.

**VS Code**: Chat panel, checkpoint-based undo, @-mention files, parallel conversations, diff viewer, auto-accept edits.

**JetBrains**: Terminal integration, native diff viewer, file references, shared configuration.

In both IDEs, Claude sees your current file, selected code, and diagnostic messages automatically.

### Custom Skills — Your Own Slash Commands

Skills encode team workflows as reusable markdown files that become slash commands.

Create `~/.claude/skills/fix-issue/SKILL.md`:

```yaml

name: fix-issue
description: Fix a GitHub issue by number
disable-model-invocation: true
---

Fix GitHub issue $ARGUMENTS following our coding standards.

2. Understand the requirements
3. Implement the fix
4. Write tests
5. Create a commit with message "fix: resolve #$ARGUMENTS"
```

Invoke: `/fix-issue 423`

Skill locations: `~/.claude/skills/` (personal), `.claude/skills/` (team-shared), plugin directories.

Advanced: `$ARGUMENTS` substitution, `context: fork` for isolated execution, `allowed-tools` restrictions, `!`command`` for dynamic context injection.

### Settings and Configuration

Five-tier hierarchy (highest to lowest precedence):

1. **Managed settings** — Admin-deployed, cannot be overridden
2. **CLI arguments** — `--allowedTools`, `--model`, etc.
3. **Project local** — `.claude/settings.local.json` (gitignored)
4. **Project shared** — `.claude/settings.json` (version-controlled)
5. **User settings** — `~/.claude/settings.json` (global)

The `.claude/` directory:

```
.claude/
├── settings.json          # Shared project settings (git)
├── settings.local.json    # Personal overrides (gitignored)
├── skills/                # Custom skills
├── agents/                # Custom sub-agents
├── rules/                 # Organized instruction files
├── hooks/                 # Hook scripts
└── worktrees/             # Isolated worktree directories
```

## Putting It All Together

Here is how the three layers compose into a daily workflow:

1. **Start the day**: `claude --resume` loads CLAUDE.md and auto-memory. *(Layer 2: External Memory)*

2. **Plan the work**: `/plan` mode explores the codebase and designs the approach before changing anything. *(Layer 2: Process Discipline)*

3. **Execute with guardrails**: Hooks auto-format and block protected files. Permissions scope what is allowed. *(Layer 2: Verification)*

4. **Parallelize**: Sub-agents with worktree isolation handle independent tasks simultaneously. *(Layer 3: Multi-Agent)*

5. **Stay sharp**: `/compact` after each task. `#` to save discoveries. *(Layer 2: External Memory)*

6. **Automate ceremony**: Commits, PRs, reviews follow CLAUDE.md conventions. *(Capability Layer)*

7. **Scale overnight**: RALPH loops iterate autonomously with completion promises. *(Layer 2: Process Discipline)*

8. **Build on top**: Agent SDK creates custom multi-agent systems for your team. *(Layer 3: Multi-Agent)*

The four bottlenecks are independent, but the solutions compose. External memory keeps context clean so process discipline can work. Process discipline structures the workflow so verification has checkpoints to verify. Multi-agent architecture multiplies all of it by running isolated agents in parallel. Each layer makes the others more effective.

Claude Code is not a chatbot. It is a scaffolding system for long-horizon autonomous agents — and understanding the bottlenecks it solves is the key to using it well.
