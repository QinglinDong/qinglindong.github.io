Claude Code is Anthropic's agentic coding assistant that lives in your terminal. Since its launch in February 2025, it has evolved from a simple chat-in-terminal experience into a full-blown autonomous development platform — with hooks, sub-agents, worktrees, MCP servers, custom skills, and an SDK for building your own agents on top of it.

This post covers every major feature, what problem it solves, and how to use it. Bookmark it. You will come back.

## The Problem Space

An AI coding agent has nine functional problems. Every feature in this post exists to solve exactly one of them.

| Area | Problem | Goal | Solutions |
|---|---|---|---|
| **Knowledge** | Agent starts every session blank — no memory of your stack, conventions, or past work | Retain project understanding across sessions | 2 |
| **Attention** | Context window fills up — quality degrades, instructions forgotten, agent drifts | Stay sharp through long sessions | 2 |
| **Autonomy** | Agent stops after each step and waits for you to prompt again | Complete multi-step work without babysitting | 4 |
| **Parallelism** | Agent does one thing at a time in one place | Run multiple tasks simultaneously without collision | 2 |
| **Reach** | Agent is blind to anything beyond local files and shell | Connect to databases, APIs, editors, CI | 2 |
| **Safety** | Autonomous agent can `rm -rf`, force-push, or corrupt state | Grant power without risking damage | 3 |
| **Ergonomics** | Every interaction requires typing full instructions from scratch | Minimize keystrokes and friction | 4 |
| **Adaptability** | Every team, project, and stack is different | Tailor behavior without forking the tool | 3 |
| **Cost** | Tokens are money with no visibility into spend or waste | Get more done per dollar | 2 |

**Cost (2)** and **Parallelism (2)** are the sparsest — the biggest opportunity gaps for new tooling and tricks. Every entry in this post maps to exactly one area. If a new trick doesn't fit any of the nine, it's opening a tenth — pay attention.

## 1. RALPH Loops — Autonomous Iteration Without Human Babysitting

### What it is

RALPH (named after Ralph Wiggum from *The Simpsons*) is an autonomous loop technique for Claude Code. In its purest form, it is a `while` loop that repeatedly feeds Claude a prompt until the task is complete. The official implementation ships as a Claude Code plugin that uses a **Stop hook** to intercept Claude's exit attempts, re-feed the original prompt, and continue the cycle.

### What problem it solves

Without RALPH, you are the loop. You give Claude a task, it finishes one step, you review, you prompt again. For large-scale work — refactoring an entire module, generating test coverage for 40 files, triaging a backlog of tickets — this human-in-the-loop overhead is the bottleneck. RALPH removes you from the loop so Claude iterates autonomously until it is genuinely done.

### How to use it

Install the plugin and invoke it:

```bash
/ralph-loop "Refactor all API handlers to use the new error format. Run tests after each file."
```

The key mechanism is a **completion promise** — a specific word or phrase (commonly `"RALPH_COMPLETE"`) that Claude outputs when it believes the task is truly finished. The Stop hook checks for this promise on every exit attempt. If it is absent, the loop continues.

Control parameters:
- `--max-iterations` — safety cap to prevent runaway loops
- `--completion-promise` — the exact string that signals done

Real-world results are striking. Geoffrey Huntley reportedly ran a 3-month RALPH loop that built a complete programming language. YC hackathon teams have shipped 6+ repos overnight for under $300 in API costs. The technique works best for batch operations: large refactors, test coverage generation, documentation sweeps, and support ticket triage.

The core insight: **verification drives everything.** Give Claude a way to verify its own work (tests, linters, type checks), and it can run reliably for hours.

RALPH is a **closed loop** — no human steering once it starts. For steerable autonomy, see Plan-File Loops below.

## 2. Plan-File Loops — Steerable Autonomy via Open Loop

### What it is

Plan-File Loops are the open-loop counterpart to RALPH. Instead of iterating silently until a completion signal, the agent writes its plan to a file (e.g. `TODO.md`, `plan.md`), works through items one by one, and checks the file for changes between iterations. The human steers by editing the file — reordering priorities, adding tasks, removing items, or leaving notes.

### What problem it solves

RALPH is powerful but unsteerable. Once a closed loop starts, you cannot redirect it without killing the session. Plan-File Loops give you a shared communication channel: the file. The agent has autonomy *within* each task, but the human controls *which* tasks and *in what order*. This is the difference between "go build everything on this list" and "go build everything and never ask me again."

### How to use it

1. Create a plan file that Claude reads at the start of each iteration:

```markdown
# Plan — Auth Refactor

- [x] Extract session logic from middleware
- [ ] Add JWT validation to /api/protected
- [ ] Write integration tests for auth flow
- [ ] Update API docs

<!-- NOTE: skip rate limiting for now, defer to v2 -->
```

2. Use a Stop hook (similar to RALPH) that re-feeds the prompt on each exit, but the prompt includes "read plan.md and work on the next unchecked item."

3. Between iterations, edit the file: reorder items, add new ones, leave `<!-- NOTE: -->` comments. The agent picks them up on the next cycle.

The key advantage: you can go to sleep and *still* wake up to redirect. Drop a note in the file from your phone, and the agent adjusts.

### When to use which

| | RALPH (closed) | Plan-File (open) |
|---|---|---|
| **Control** | None after launch | Edit the file anytime |
| **Best for** | Uniform batch work (same operation × many files) | Multi-step projects with changing priorities |
| **Risk** | Runaway loops, wasted work on wrong path | Agent may re-read file too often, slight overhead |
| **Human role** | Set and forget | Light supervision via file edits |

## 3. Hooks — Deterministic Control Over Non-Deterministic Behavior

### What it is

Hooks are user-defined shell commands that execute at specific lifecycle points in Claude Code. They fire deterministically — you are not *hoping* Claude remembers to run Prettier; it *always* runs because the hook guarantees it.

### What problem it solves

LLMs are probabilistic. You can tell Claude "always format with Prettier after editing a file" in your CLAUDE.md, and it will do it 90% of the time. Hooks make it 100%. They also enable workflows that Claude cannot initiate on its own: desktop notifications, audit logging, blocking edits to protected files, and re-injecting context after compaction.

### Hook event lifecycle

| Event | When it fires |
|---|---|
| `SessionStart` | Session begins or resumes (including after compaction) |
| `UserPromptSubmit` | After you press Enter, before Claude processes |
| `PreToolUse` | Before a tool call executes — **can block it** |
| `PostToolUse` | After a tool call succeeds |
| `Stop` | When Claude finishes responding |
| `Notification` | When Claude needs your attention |
| `SubagentStart` / `SubagentStop` | When sub-agents spawn or finish |
| `ConfigChange` | When a settings file changes |
| `PreCompact` | Before context compaction |
| `SessionEnd` | When the session terminates |

### Practical examples

**Auto-format after every edit** (PostToolUse):

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}
```

**Block edits to protected files** (PreToolUse — exit code 2 blocks the action):

```bash
#!/bin/bash
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')
PROTECTED=(".env" "package-lock.json" ".git/")
for pattern in "${PROTECTED[@]}"; do
  if [[ "$FILE_PATH" == *"$pattern"* ]]; then
    echo "Blocked: $FILE_PATH matches protected pattern '$pattern'" >&2
    exit 2
  fi
done
exit 0
```

**Desktop notification when Claude is waiting** (Notification):

```json
{
  "hooks": {
    "Notification": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "osascript -e 'display notification \"Claude Code needs your attention\" with title \"Claude Code\"'"
          }
        ]
      }
    ]
  }
}
```

There are also **prompt-based hooks** (`"type": "prompt"`) where a small Claude model makes a yes/no decision, and **agent-based hooks** (`"type": "agent"`) where a sub-agent with full tool access verifies conditions before allowing the action.

## 4. MCP Servers — Connecting Claude to Everything

### What it is

MCP (Model Context Protocol) is an open standard created by Anthropic that lets Claude Code connect to external tools — databases, browsers, APIs, internal services — via a unified protocol. Think of it as USB for AI tools: one plug, many devices.

### What problem it solves

Without MCP, Claude Code can only interact with your local filesystem and shell. With MCP, it can query your database, browse the web, search your company's Confluence, interact with GitHub's API natively, manage your cloud infrastructure, and more — all through the same natural-language interface.

### How to use it

Add an MCP server from the command line:

```bash
claude mcp add github -- npx -y @modelcontextprotocol/server-github
```

Or configure it in `.mcp.json` at your project root (version-controlled):

```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    }
  }
}
```

MCP supports three transport modes: **stdio** (default, simplest), **SSE** (Server-Sent Events), and **Streamable HTTP**.

**Tool Search** is a key optimization: when your MCP tool descriptions would consume more than 10% of the context window, Claude Code automatically enables dynamic tool loading. Instead of pre-loading all tool descriptions, it searches for the right tool on demand.

Configuration scopes: project-scoped (`.mcp.json`), project-specific (`.claude/settings.local.json`), or user-specific (`~/.claude/settings.local.json`).

## 6. CLAUDE.md Files — Teaching Claude Your Project's DNA

### What it is

CLAUDE.md is a markdown file that Claude reads automatically at the start of every session. It contains persistent context about your project: coding conventions, architecture decisions, build commands, testing instructions, and anything else you would otherwise repeat in every prompt.

### What problem it solves

Without CLAUDE.md, every new Claude Code session starts from zero. You have to re-explain your stack, your conventions, your file structure. CLAUDE.md gives Claude institutional memory — it knows your project before you say a word.

### The memory hierarchy

| Level | Location | Scope |
|---|---|---|
| User memory | `~/.claude/CLAUDE.md` | All your projects. Global preferences. |
| Project memory | `CLAUDE.md` at repo root | This repo. Tech stack, patterns, build commands. Version-controlled. |
| Rules directory | `.claude/rules/*.md` | Organized, focused rule files for larger projects. |
| Nested directories | `packages/frontend/.claude/rules/` | Monorepo support. Package-specific rules. |

### How to set it up

Run `/init` to generate a starter CLAUDE.md, then customize it:

```markdown
# Project: MyApp

## Tech Stack
- TypeScript, React 18, Next.js 14 App Router
- Tailwind CSS for styling
- Prisma ORM with PostgreSQL
- Vitest for testing

## Conventions
- Use named exports, not default exports
- All API routes return `{ data, error }` shape
- Commit messages follow Conventional Commits
- Never use `any` type — use `unknown` and narrow

## Common Commands
- `pnpm dev` — start dev server
- `pnpm test` — run test suite
- `pnpm lint` — run ESLint + Prettier check
- `pnpm db:migrate` — run Prisma migrations
```

**Quick memory addition**: Press `#` during a session to add a memory. Type your instruction and hit Enter — Claude writes it to the appropriate CLAUDE.md.

## 7. Plan Mode — Think Before You Act

### What it is

Plan Mode restricts Claude to read-only operations. It can analyze your codebase using Glob, Grep, and Read, but it cannot edit files, run commands, or modify anything. It creates a detailed implementation plan and waits for your approval before executing.

### What problem it solves

For complex changes — refactoring auth, migrating a database schema, restructuring a module — you do not want Claude to start changing files immediately. You want to see the plan first, challenge it, refine it, and *then* execute. Plan Mode prevents premature action and gives you a review checkpoint.

### How to activate it

Three ways:
1. **Press `Shift+Tab` twice** — cycles through Normal → Auto-Accept → Plan Mode
2. **Type `/plan`** — enters Plan Mode directly
3. **Set in config** — `defaultMode: "plan"` in settings.json

When active, you will see `plan mode on` at the bottom of the terminal. Claude explores the codebase, reads files, searches patterns, and outputs a structured plan with specific files, changes, and rationale.

To exit: press `Shift+Tab` again. Claude will ask for confirmation before executing.

## 8. Worktrees — Parallel Development Without Collisions

### What it is

Git worktrees create separate working directories that each have their own files and branch, while sharing the same repository history. Claude Code has native support for worktrees, allowing multiple Claude sessions to work on the same repo simultaneously without interfering with each other.

### What problem it solves

If you run two Claude sessions against the same directory, their file edits collide. One session writes a file, the other overwrites it. Worktrees solve this by giving each session its own isolated copy of the codebase.

### How to use it

From the CLI:

```bash
claude --worktree feature-auth
```

This creates a worktree at `.claude/worktrees/feature-auth` with a new branch, and starts Claude in that directory.

For sub-agents, add `isolation: worktree` to the agent's frontmatter, or ask Claude to "use worktrees for your agents." Each sub-agent then works in its own worktree, preventing merge conflicts between parallel tasks.

For non-git version control (SVN, Perforce, Mercurial), configure `WorktreeCreate` and `WorktreeRemove` hooks with your custom logic.

## 9. Sub-Agents and the Task Tool — Divide and Conquer

### What it is

Sub-agents are specialized AI assistants that Claude can spawn to handle specific tasks. Each runs in its own context window with a custom system prompt, specific tool access, and independent permissions. The Task tool is how Claude dispatches work to these agents.

### What problem it solves

A single conversation context gets crowded fast. If Claude is implementing a feature, debugging a test, and researching an API simultaneously, the context window fills up and quality degrades. Sub-agents keep each concern isolated: the research happens in one context, the implementation in another, and the main agent stays clean.

### Three execution modes

1. **Parallel** — 3+ independent tasks with no shared state. Claude fans out to multiple sub-agents simultaneously.
2. **Sequential** — Tasks with dependencies. Output from agent A feeds into agent B.
3. **Background** — Research or analysis that is not blocking your current work. Results surface when ready.

### Built-in agent types

| Agent | Purpose |
|---|---|
| `Explore` | Read-only codebase exploration. Uses Glob, Grep, Read. |
| `Plan` | Creates implementation plans without modifying files. |
| `general-purpose` | Full tool access. The default. |

### Custom sub-agents

Create `.claude/agents/security-reviewer/AGENT.md`:

```yaml
---
name: security-reviewer
description: Reviews code changes for security vulnerabilities
model: claude-sonnet-4-20250514
allowed-tools: Read, Grep, Glob
---

You are a security engineer. Review the provided code for:
1. Injection vulnerabilities (SQL, XSS, command)
2. Authentication/authorization issues
3. Sensitive data exposure
4. Insecure dependencies

Report findings with severity, file location, and remediation.
```

### Background execution

Press `Ctrl+B` while an agent is running to move it to the background. Use `/tasks` to see all running background processes. This lets you continue working in the main conversation while sub-agents research, analyze, or build in parallel.

## 10. Permission Modes — Safety at Scale

### What it is

Claude Code has a tiered permission system that controls what Claude can do. Read-only operations (file reads, grep) require no approval. Bash commands require per-invocation approval. File modifications require session-level approval.

### What problem it solves

You want Claude to be autonomous enough to be useful, but safe enough not to `rm -rf` your repo. The permission system lets you dial the trust level exactly where you need it — from fully manual approval to fully autonomous execution.

### Permission modes

| Mode | Behavior |
|---|---|
| `default` | Prompts for permission on first use of each tool. |
| `acceptEdits` | Auto-accepts file edits. Still prompts for bash. |
| `plan` | Read-only. No modifications. No commands. |
| `dontAsk` | Auto-denies anything not explicitly allowed via rules. |
| `bypassPermissions` | Skips all prompts. **Only use in sandboxed environments.** |

### Allowlist and denylist

Configure in `settings.json`:

```json
{
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(git commit *)",
      "Bash(pnpm test *)",
      "Read"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Bash(git push --force *)",
      "Edit(.env)"
    ]
  }
}
```

Rules evaluate in order: **deny > ask > allow**. The first match wins. You can use wildcard patterns (`*`), and the syntax is aware of shell operators — `Bash(safe-cmd *)` will not allow `safe-cmd && rm -rf /`.

Toggle with `Shift+Tab` during a session, or use `/permissions` to view and modify rules.

## 11. Auto-Memory — Claude Writes Notes to Itself

### What it is

Auto-memory is a persistent directory where Claude records learnings, patterns, and insights *as it works*. Unlike CLAUDE.md (which you write for Claude), auto-memory contains notes Claude writes for itself based on what it discovers during sessions.

### What problem it solves

Claude has no memory between sessions by default. Auto-memory bridges this gap by letting Claude record what it learns — project patterns, key commands, architectural decisions — and load those notes at the start of every future session.

### How it works

Each project gets its own memory directory at `~/.claude/projects/<project-hash>/memory/`. The first 200 lines of the main memory file (`MEMORY.md`) are loaded into Claude's system prompt at every session start.

Claude writes to memory when it discovers something worth remembering: a non-obvious build command, an architectural pattern, a preference you expressed. You can also manually trigger memory saves by pressing `#` and typing an instruction.

The memory hierarchy:
- **Auto-memory**: Notes Claude writes for itself
- **User CLAUDE.md**: Global preferences you write (`~/.claude/CLAUDE.md`)
- **Project CLAUDE.md**: Project-specific instructions you write (repo root)
- **Rules directory**: Organized rule files (`.claude/rules/`)

## 14. Tool Use Patterns — The Right Tool for the Job

### What it is

Claude Code has dedicated tools for different operations. Using the right tool matters for performance, permissions, and reliability.

### What problem it solves

Using `cat` via Bash to read a file bypasses the permission system, wastes context on shell overhead, and makes it harder for Claude to track what it has read. The dedicated tools are optimized for the agent loop.

### Tool hierarchy

| Task | Use This | Not This |
|---|---|---|
| Search for files by name | **Glob** (`**/*.ts`) | `find` via Bash |
| Search file contents | **Grep** (regex patterns) | `grep` or `rg` via Bash |
| Read a file | **Read** (with line ranges) | `cat` / `head` / `tail` via Bash |
| Edit part of a file | **Edit** (string replacement) | `sed` / `awk` via Bash |
| Write a new file | **Write** (full content) | `echo >` via Bash |
| Run commands | **Bash** | N/A |

### Why this matters

1. **Permissions**: Read and Edit go through the permission system. `cat` via Bash does not.
2. **Context efficiency**: Glob returns just file paths. `find` via Bash returns paths plus shell boilerplate.
3. **Parallel execution**: Claude can batch multiple Glob and Grep calls in a single turn. Bash commands are sequential.
4. **Hooks**: PreToolUse and PostToolUse hooks can trigger on Edit or Write. They cannot trigger on `sed` run through Bash.

### The batch pattern

When Claude needs multiple pieces of information, it should dispatch multiple tool calls in parallel:

```
[Grep("error handler", "src/"), Glob("**/*.test.ts"), Read("package.json")]
```

This is faster than three sequential Bash calls and produces cleaner context.

## 15. Git Workflows — Commits, PRs, and Branch Management

### What it is

Claude Code has deep git integration. It can create commits with intelligent messages, create pull requests via `gh`, manage branches, and review code changes.

### What problem it solves

Git ceremonies are repetitive. Writing commit messages, creating PRs with proper descriptions, handling branch management — Claude automates all of it while respecting your project's conventions.

### Creating commits

Ask Claude naturally:

```
Look at my staged changes and create an appropriate commit.
```

Claude examines every modified file, identifies which changes belong together, and proposes separate commits if the changes are logically distinct. It generates messages following your conventions (Conventional Commits, etc. — specify in CLAUDE.md).

In headless mode:

```
Create a PR for the current branch with a detailed description.
```

Claude analyzes all commits since the branch diverged, drafts a title (under 70 characters) and a structured body with a summary and test plan, and creates the PR via `gh pr create`.

### Code review

```
/review
```

Or more specifically:

```
Review the changes on this branch for security issues and performance problems.
```

### Best practices

- Specify your commit message convention in CLAUDE.md
- Use a naming scheme for Claude-created branches (e.g., `claude/[feature]-[session-id]`)
- Create draft PRs to review before marking ready
- Claude appends `Co-Authored-By: Claude` to commits it creates

## 16. Context Management — Keeping Claude Sharp

### What it is

Claude Code has a finite context window. As your conversation grows, so does the token count per message. Context management is the set of tools and techniques for keeping the context window clean and focused.

### What problem it solves

Context degradation is the primary failure mode of long Claude Code sessions. As the window fills up, response quality drops, costs increase, and Claude starts forgetting earlier instructions. Active context management prevents this.

### /compact — Conversation compression

```
/compact
```

Claude summarizes the entire conversation, preserving key decisions and discarding redundant detail. You can provide focus instructions:

```
/compact Focus only on the authentication refactor. Discard everything about styling.
```

Compaction is now nearly instant — Claude maintains a continuous background summary, so `/compact` just loads that summary into a fresh context.

**Auto-compact** triggers when the context window reaches approximately 95% capacity. But do not wait for it. Best practice: **run `/compact` every time you finish a task** before starting the next one.

### /clear — Hard reset

```
/clear
```

Wipes everything. Use this when switching to a completely unrelated task.

### /context — Visualization

```
/context
```

Shows a colored grid of what is consuming your context window. Useful for diagnosing why Claude seems confused.

### Re-inject context after compaction

Use a `SessionStart` hook with a `compact` matcher to restore critical context that compaction might lose:

```json
{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "compact",
        "hooks": [
          {
            "type": "command",
            "command": "echo 'Reminder: use Bun, not npm. Run bun test before committing.'"
          }
        ]
      }
    ]
  }
}
```

## 17. Custom Skills — Your Own Slash Commands

### What it is

Skills are reusable instruction sets you create as markdown files. They become slash commands (`/skill-name`) and can also be auto-loaded by Claude when relevant. Custom slash commands (`.claude/commands/`) have been merged into skills — both approaches create `/commands` and work the same way.

### What problem it solves

Every team has repetitive workflows: deploy to staging, create a migration, run the security audit, generate a changelog. Skills encode these workflows once and let anyone on the team invoke them consistently.

### Creating a skill

Create `~/.claude/skills/fix-issue/SKILL.md`:

```yaml
---
name: fix-issue
description: Fix a GitHub issue by number
disable-model-invocation: true
---

Fix GitHub issue $ARGUMENTS following our coding standards.

1. Read the issue description with `gh issue view $ARGUMENTS`
2. Understand the requirements
3. Implement the fix
4. Write tests
5. Create a commit with message "fix: resolve #$ARGUMENTS"
```

Invoke it: `/fix-issue 423`

### Skill locations

| Location | Scope |
|---|---|
| `~/.claude/skills/<name>/SKILL.md` | All your projects (personal) |
| `.claude/skills/<name>/SKILL.md` | This project only (team-shared via git) |
| Plugin `skills/` directory | Where the plugin is enabled |

### Advanced features

- **`$ARGUMENTS`** — string substitution for parameters
- **`context: fork`** — run the skill in an isolated sub-agent
- **`allowed-tools`** — restrict what tools the skill can use
- **`disable-model-invocation: true`** — only you can trigger it (not Claude)
- **`!`command``** — dynamic context injection; shell commands run before the skill is sent to Claude
- **Supporting files** — templates, examples, scripts in the skill directory

## 18. Settings and Configuration — The Control Panel

## 19. Headless Mode — Claude Without a Human

### What it is

The `-p` (or `--print`) flag runs Claude Code non-interactively. It executes a single query, outputs the result, and exits. This is the foundation for CI/CD integration, scripting, and building automation on top of Claude.

### What problem it solves

Interactive mode requires a human at the terminal. Headless mode lets you embed Claude in scripts, GitHub Actions, GitLab CI/CD, cron jobs, and automated pipelines — anywhere you need an AI agent without a human in the loop.

### Basic usage

```bash
# Simple question
claude -p "What does the auth module do?"

# Pipe input
cat error.log | claude -p "What caused this crash?"

# Structured JSON output
claude -p "Extract function names from auth.py" \
  --output-format json \
  --json-schema '{"type":"object","properties":{"functions":{"type":"array","items":{"type":"string"}}}}'

# PR review in CI
gh pr diff "$PR_NUMBER" | claude -p \
  --append-system-prompt "You are a security engineer. Review for vulnerabilities." \
  --output-format json

# Auto-approve specific tools
claude -p "Run tests and fix failures" \
  --allowedTools "Bash,Read,Edit"
```

### Continuing conversations

```bash
# First request
claude -p "Review this codebase for performance issues"

# Continue the same conversation
claude -p "Now focus on database queries" --continue

# Or capture and resume a specific session
session_id=$(claude -p "Start review" --output-format json | jq -r '.session_id')
claude -p "Continue review" --resume "$session_id"
```

### Streaming output

```bash
claude -p "Explain recursion" \
  --output-format stream-json \
  --verbose \
  --include-partial-messages
```

**Important security note**: In `-p` mode, trust verification is disabled. First-time codebase runs and new MCP servers execute without trust prompts. Use `--allowedTools` to scope permissions explicitly.

## 20. Multi-Turn Agentic Workflows — How Claude Chains Actions

### What it is

Claude Code does not just answer questions. It works through tasks in a loop: **gather context, take action, verify results**, blending these phases as it chains dozens of tool calls together, course-correcting based on each result.

### What problem it solves

Traditional coding assistants generate code and hand it to you. You paste it in, run it, find the bug, go back to the assistant, paste the error, wait for a fix. Claude Code eliminates this round-trip by doing the entire cycle itself: write code, run tests, read errors, fix code, verify, repeat.

### The agentic loop

```
You: "Add rate limiting to the API"

Claude: [Read src/routes/api.ts]
        [Grep "middleware" across codebase]
        [Read src/middleware/auth.ts for pattern reference]
        [Edit src/middleware/rateLimit.ts — create new file]
        [Edit src/routes/api.ts — add middleware]
        [Bash: npm test]
        [Read test output — 2 failures]
        [Edit src/middleware/rateLimit.ts — fix edge case]
        [Bash: npm test]
        [All tests pass]
        "Done. Added rate limiting middleware with sliding window..."
```

Each step informs the next. Claude reads test output and uses it to fix bugs. It reads existing patterns in your codebase and follows them. It does not guess — it verifies.

### The three phases

1. **Gather context**: Glob for files, Grep for patterns, Read for content. Claude builds a mental model of your codebase.
2. **Take action**: Edit files, write new files, run commands. Claude implements the change.
3. **Verify results**: Run tests, check types, lint. Claude confirms the change works.

These phases are not linear. They interleave. Claude might gather more context mid-implementation when it discovers something unexpected. This is what makes it agentic rather than generative.

## 21. The Agent SDK — Build Your Own Agents

### What it is

The Claude Agent SDK exposes the same engine that powers Claude Code — the agent loop, built-in tools, context management — as a library you can use in TypeScript or Python to build your own agents.

### What problem it solves

Claude Code is designed for interactive terminal use. But what if you want an AI agent embedded in your web app? Or a custom CI bot? Or a specialized review agent that runs on every PR? The SDK gives you the building blocks without reinventing the agent loop.

### Installation

```bash
npm install @anthropic-ai/claude-agent-sdk
```

### Basic usage (TypeScript)

```typescript
import { query } from "@anthropic-ai/claude-agent-sdk";

const messages = query({
  prompt: "Find and fix security vulnerabilities in auth.py",
  allowedTools: ["Read", "Edit", "Bash"],
  options: {
    maxTurns: 20,
  },
});

for await (const message of messages) {
  console.log(message);
}
```

### Key concepts

- **`query` function** — the main entry point. Returns an async iterator that streams messages as Claude works.
- **Built-in tools** — same tools as Claude Code (Read, Edit, Write, Bash, Glob, Grep).
- **Custom sub-agents** — define agents programmatically with system prompts, tool access, and permissions.
- **Programmatic configuration** — no filesystem dependencies. Define everything in code.
- **The V2 interface** (preview) removes async generators; each turn is a separate `send()`/`stream()` call.

The SDK lets you build agents that are not just coding assistants — they can be customer support bots, data pipeline monitors, infrastructure managers, or anything else you can describe in a system prompt and equip with tools.

## Putting It All Together — A Power User's Daily Workflow

Here is how these features compose into a real development workflow:

1. **Start the day**: `claude --resume` to pick up where you left off, or `claude` in a project with a well-written CLAUDE.md.

2. **Plan the work**: Use Plan Mode (`/plan` or `Shift+Tab` twice) to explore the codebase and design the approach before changing anything.

3. **Execute with guard rails**: Switch to normal mode. Allowlist your safe commands in permissions. Let Claude work. Hooks auto-format code and block edits to protected files.

4. **Parallelize**: For independent tasks, let Claude spawn sub-agents with worktree isolation. Feature in one worktree, bug fix in another.

5. **Stay sharp**: Run `/compact` after completing each task. Use `/context` to monitor usage. Press `#` to save important discoveries to memory.

6. **Automate the ceremony**: Let Claude handle commits (`/commit`), PR creation, and code review. Your CLAUDE.md defines the conventions it follows.

7. **Scale overnight**: For large batch work, use RALPH loops. Set a completion promise, configure a max iteration count, and let Claude iterate autonomously.

8. **Build on top**: Use the Agent SDK to create custom agents for your team's specific workflows — PR reviewers, migration helpers, security auditors.

Claude Code is not a chatbot. It is a development platform. The features above are not independent — they are a system. The more of them you use together, the more powerful each one becomes.
